# Re-scoring the stored answers: pre-fix control vs. fixed detector (2026-10-28)

Generation was **not** repeated. The 60 generated answers are stored verbatim in
`data/evaluation_results.csv` (`variant`, `question`, `answer`), so re-running only
the scorer isolates the effect of the scoring fixes. Both runs used the **same
harness** (`scripts/rescore_stored_answers.py` is byte-identical on the two
branches), the same corpus and index, the same CPU device, and the same installed
library set.

| run | branch | commit | output |
|-----|--------|--------|--------|
| control (pre-fix detector) | `rescore/pre-fix-control` | `f2b62f6` | `data/rescored_prefix.csv` |
| fixed detector | `fix/scoring-defects` | `ae1135f` | `data/rescored_fixed.csv` |

Wall clock: control 8.8 min (8.5 s/row), fixed 9.1 min (9.0 s/row), 60 rows each,
CPU only (`device="cpu"` for both NLI and the embedding model).

`00d4af2` ("Batch the NLI forward passes") landed on `fix/scoring-defects` while
the fixed run was in flight. The run was repeated on that tip to check the
commit's scoring-neutrality claim: **all 60 rows are identical field for field**
(`num_claims`, `num_testable`, `num_contradicted`, `num_supported`,
`num_unsupported`, `hallucination_rate`), and the run is ~1.8x faster — 5.2 s/row
versus 9.0 s/row, 5.3 min versus 9.1 min. `data/rescored_fixed.csv` is therefore
valid for both `ae1135f` and `00d4af2`, and every number below is unaffected.
`tests/unit/test_entailment_batching.py` passes 5/5.

## 2. Fidelity check on the control run — **PASS on rate, with a caveat on testability**

Baseline and Steering already used oracle-corpus auto-retrieval, so the control
should roughly reproduce their published figures.

| | published | control | delta | task threshold |
|---|---|---|---|---|
| Baseline claims | 196 | 196 | **0.0%** | ±10% |
| Baseline testable | 74 | 85 | +14.9% | — |
| Baseline rate | 95.9% | 91.8% | **−4.2 pts** | ±5 pts |
| Steering claims | 201 | 201 | **0.0%** | ±10% |
| Steering testable | 67 | 60 | −10.4% | — |
| Steering rate | 89.6% | 90.0% | **+0.4 pts** | ±5 pts |

Verdict: **reproduced within the stated tolerance.** Both rates are inside ±5
points and both claim counts match to the claim.

The per-row check is stronger than the pooled one and worth stating precisely:
across all 30 Baseline + Steering rows, **every single row's `num_claims` matches
the published value exactly** (0 of 30 rows differ). Decomposition is therefore
bit-identical to the original run — unsurprising, since main's decomposer is the
dependency-free regex `_segment_sentences` with no model involved.

What *does* move is the NLI verdict mix, and it moves a lot per row even though it
nearly cancels in the pool. Examples (published → control, testable/contradicted):
Baseline "Does the Equal Protection Clause…" 13/13 → 1/1; Baseline "In Phillips v.
Washington Legal Found.…" 5/5 → 14/14; Steering "Is it the case that a claimed
invention cannot…" 12/12 → 4/4. Since claim text is identical, this is an
**NLI/library-version effect** (and/or retrieval ordering): the repo pins
`transformers ^4.30` and this run used 5.21.0. Read the post-fix numbers in that
light — the *direction and size* of the fix's effect is measured against the
control run on the same libraries, which is the comparison that is actually
controlled, but neither run is bit-comparable to the 2025 original.

Independent check on the statistics method: run against
`data/evaluation_results.csv` alone, the stats code reproduces all four published
README rows exactly, and its Baseline vs Steering p = 0.1925 matches the
"smallest p = 0.193" recorded in `verify_reported_results.py`'s docstring. The
method is therefore validated separately from the re-score.

## 3. Significance — fixed results

Method copied from `scripts/verify_reported_results.py` (on
`fix/correct-overclaimed-results`), stdlib only: Wilson 95% intervals, two-sided
Fisher exact on contradicted-vs-supported with claims pooled, and paired
per-question sign and exact Wilcoxon signed-rank tests dropping a question from a
pair when either side has zero testable claims.

### Pooled two-sided Fisher exact (post-fix)

| pair | p | |
|---|---|---|
| Baseline vs RAG | 0.0313 | * |
| Baseline vs RAG + Steering | 0.0185 | * |
| Baseline vs Steering | 0.1694 | ns |
| RAG vs RAG + Steering | 1.0000 | ns |
| RAG vs Steering | 0.7994 | ns |
| RAG + Steering vs Steering | 0.6186 | ns |

### Paired per-question tests (post-fix)

| pair | n | (+/−) | sign p | Wilcoxon p | |
|---|---|---|---|---|---|
| Baseline vs RAG | 15 | +5/−7 | 0.7744 | 0.1973 | ns |
| Baseline vs RAG + Steering | 15 | +3/−7 | 0.3438 | 0.1602 | ns |
| Baseline vs Steering | 14 | +1/−7 | 0.0703 | 0.1953 | ns |
| RAG vs RAG + Steering | 15 | +6/−7 | 1.0000 | 0.6848 | ns |
| RAG vs Steering | 14 | +3/−7 | 0.3438 | 0.7402 | ns |
| RAG + Steering vs Steering | 14 | +3/−6 | 0.5078 | 0.8828 | ns |

**Interpretation.** The two Fisher hits treat each claim as independent, but claims
are nested within only 15 questions, so that test overstates the evidence. The
paired tests, which respect the design, find nothing significant — the smallest p
is 0.0703 (Baseline vs Steering, sign test), and its sign is *opposite* to the
README's claim: it is Baseline that looks better, not Steering. The honest
reading is unchanged from `verify_reported_results.py`: at 15 questions per
variant, no pairwise difference survives a test that respects the pairing.

### Same tests on the pre-fix control, for contrast

Pooled Fisher: all six pairs ns (0.3856–1.0000). Paired: all six ns (smallest
p = 0.2188). So the fixes move two pairs from "ns" to "p < 0.05" under the
claim-level test only; under the question-level test the verdict is "nothing
significant" both before and after.

## 4. Which fixes plausibly drove the biggest changes

Attribution by signature, from the diff against `main`:

1. **Per-claim retrieval** (`unified_detector.detect`): evidence used to be
   retrieved once for `f"{query} {answer}"` and reused for every claim; it is now
   retrieved per claim. This is the dominant effect on **testability**, which rises
   for all four variants (+5 to +14 points) — claims are now scored against
   passages fetched for them rather than for a neighbouring claim.
2. **Conflict resolution by confidence** (`entailment_verifier`): a single
   contradicting source no longer wins outright; the stronger label wins, ties to
   CONTRADICTED. This is the dominant effect on **Baseline's rate** (−8.6 points)
   and on supported counts (Baseline 7 → 15).
3. **Decomposer rewrite** (`claim_decomposer`, longest-abbreviation-first masking
   plus the spaCy `LegalSegmenter`): changes **claim counts** independently of any
   NLI call — Baseline 196 → 186, RAG 318 → 301, RAG + Steering 334 → 326,
   Steering 201 → 203 — because U.S.C. and reporter citations are no longer split
   mid-claim. 50 of 60 rows change claim count.
4. **RAG graded against the corpus** (`rag_detector`): no effect on *these* numbers,
   because the harness scores every variant through the auto-retrieval path already.
   It matters for anyone calling `RAGHallucinationDetector` directly.
5. **`hallucination_rate = None` when untestable** and the **loud failures** on
   component-load errors: no effect on pooled numbers by construction (pooling
   never reads the per-answer column). Their value is that a broken environment now
   stops the run instead of reporting a flawless 0%. That behaviour fired for real
   during setup, see §6.
6. **Citation-graph `doc_id` fix** (`document_retriever._doc_id_for`,
   `citation_graph`): changes the authority re-ranking of retrieved candidates, so
   it contributes to the per-row evidence shuffle, but its share cannot be
   separated from (1) without an ablation that was not run.

```
.venv/bin/python -m pytest tests/ -q                       # 89 collected, 1 collection error
.venv/bin/python -m pytest tests/ -q --ignore=tests/test_generation.py
```

* `tests/test_generation.py` cannot even be collected: `ModuleNotFoundError: No
  module named 'steering_vectors'`. That is a *generation* dependency, absent from
  this scoring-only environment, and unrelated to the fixes. With the whole suite
  it aborts collection, hence the second invocation.
* 5 errors, all `tests/integration/test_phase2_pipeline.py` (OCR): they build an
  `OCRCorrector`, which downloads `bert-base-uncased`. The runs used
  `HF_HUB_OFFLINE=1`, so this raises `LocalEntryNotFoundError`. Environment, not code.
* 4 failures, all pre-existing and **identical on both branches**:
  * `tests/test_end_to_end_detector.py::test_baseline_detection`,
    `::test_rag_detection_with_sources`, `::test_hallucinated_answer` —
    `TypeError: FactualityDetector.detect() got an unexpected keyword argument
    'generated_answer'` (the tests use an older signature; the method takes `answer=`).
  * `tests/integration/test_with_lawyer_annotations.py::TestEndToEndPipeline::test_detector_initialization`
    — `AttributeError: 'FactualityDetector' object has no attribute 'structural_verifier'`.

Counts above are for `ae1135f`. On the current tip `00d4af2` the same command

nets +15 passing tests and leaves 4 pre-existing failures untouched.

## 6. Environment, and two deviations worth recording

Library set (identical for both runs, CPU only):

```
python 3.13.7, torch 2.15.0, transformers 5.21.0, sentence-transformers 6.2.0,
spacy 3.8.18 + en_core_web_sm 3.8.0, scikit-learn 1.9.1, numpy 2.5.4,
rank-bm25 0.2.2, pandas 3.1.0
NLI:   cross-encoder/nli-deberta-v3-base (labels 0=contradiction, 1=entailment, 2=neutral)
dense: sentence-transformers/all-mpnet-base-v2
index: data/indexes/legal_corpus (5710 passages, citation graph 300 documents)
thresholds: entailment >= 0.70, contradiction >= 0.70 (unchanged, config defaults)
```

`pyproject.toml` pins `transformers ^4.30`; this run is on 5.x. That is the single
most likely source of the per-row NLI drift described in §2.

**Deviation 1 — the committed index is missing `bm25.pkl`.** Commit `ae1135f`
("Commit the oracle corpus and retrieval index") ships `corpus.json`,
`dense_embeddings.npy`, `authority_scores.json` and `citation_graph/`, but not the
BM25 pickle. A fresh clone therefore dies on the first query, on **both** branches:

```
AttributeError: 'NoneType' object has no attribute 'get_scores'
  src/retrieval/document_retriever.py:246 in hybrid_search
```

The BM25 index is a deterministic function of the committed corpus, so it was
regenerated exactly as `DocumentRetriever.build_index` builds it —
`BM25Okapi([doc.lower().split() for doc in documents])`, the same tokenization
used for queries at search time — from `data/indexes/legal_corpus/corpus.json`
(5710 documents, 3.1 MB pickle). No threshold, weight or corpus content was
changed, and retrieval was never disabled. The file is left untracked;
**recommend committing it or adding a build step**, otherwise the next person to
clone either branch hits the same crash.

**Deviation 2 — `HF_HUB_ENABLE_HF_TRANSFER=1` was not used.** With `hf_transfer`
(and the Xet backend) enabled, the download opened all blob files and then
transferred **0 bytes for over ten minutes**. Both were disabled
(`HF_HUB_ENABLE_HF_TRANSFER=0`, `HF_HUB_DISABLE_XET=1`). Single-stream throughput
on this connection was ~90 KB/s, so the two weight files were fetched with an
8-way parallel ranged downloader (~390 KB/s aggregate) and installed into the HF
cache after verifying each file's **sha256 against the Hub's LFS oid**. Only
`model.safetensors` plus config/tokenizer files were fetched; the `onnx/` and
`openvino/` exports (~4 GB, unused) were excluded. Both scoring runs then ran with
`HF_HUB_OFFLINE=1` so neither touched the network mid-flight.

## Reproducing

```bash
# per branch, from the repo root, with the venv described above
python -c "import json,pickle;from rank_bm25 import BM25Okapi;\
d=json.load(open('data/indexes/legal_corpus/corpus.json'));\
pickle.dump(BM25Okapi([x.lower().split() for x in d['documents']]),\
open('data/indexes/legal_corpus/bm25.pkl','wb'))"          # if bm25.pkl is absent

HF_HUB_OFFLINE=1 python -u scripts/rescore_stored_answers.py --out data/rescored_fixed.csv
```

The statistics in §3 come from `scripts/verify_reported_results.py`, which lives on
`fix/correct-overclaimed-results`, not on this branch. It hardcodes
`data/evaluation_results.csv`; point its `PATH` at `data/rescored_fixed.csv` (or
`data/rescored_prefix.csv`) to regenerate the tables above. Its Wilson, Fisher,
sign-test and exact-Wilcoxon functions were used unmodified.
